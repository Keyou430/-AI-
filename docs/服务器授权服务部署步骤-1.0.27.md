# 服务器授权服务部署步骤

适用版本：视频二创 AI 助手 1.0.27
整理日期：2026年11月5日
适用人员：服务器运维、实施人员、平台管理员

本文用于部署集中账号授权服务，并将 Windows 客户端接入该服务。实施顺序为准备环境、部署服务、配置 HTTPS、验收接口、安装绑定客户端、验收账号权限，最后建立备份与恢复流程。正文为待执行步骤，不表示本次已在生产环境实施。

## 1 版本依据与部署目标

### 1.1 采用的版本依据

已核对当前源码 package.json、1.0.27 安装脚本、release/latest.yml 和 release/universal-package-acceptance-1.0.27.json。安装包为 video-remix-universal-setup-1.0.27.exe，大小为 144434123 字节，SHA256 为：

~~~text
00f39d506a8fc7716b3271bdf6ab374fc7e6a51112bd7203945e82b745298263
~~~

对应验收记录记载：258 项源码测试通过、12 项安装 PowerShell 用例通过、6 项 NSIS 钩子用例通过，正式包桌面与供应商配置检查通过。这些是已有本地记录；目标服务器、真实员工设备及商业供应商仍须按本文验收。

release/universal-delivery.json 和部分旧文档仍写 1.0.26，不作为本手册的安装包版本依据。旧《企业交付平台部署操作手册》以 1.0.19 为基线，不能直接套用其中的客户端绑定说明。

### 1.2 架构与成功标准

员工客户端通过 HTTPS 访问授权服务；Caddy 或已有 Nginx 反向代理到 127.0.0.1:3080。服务负责登录、身份与角色、账号管理、会话撤销及相关日志，不代理智能二创、内容提取、图片生成，不保存员工 API Key、知识库或生成内容。

客户端直接连接供应商，本机保存历史、业务背景、关键词、知识库、素材及加密接口配置。管理员和成员使用同一份 Windows x64 安装包，权限由服务端账号角色决定。

成功标准：服务开机自启；3080 只监听回环地址；HTTPS 证书校验正常；两个安装探测接口返回预期结果；空库能初始化管理员；管理员能管理账号、成员不能管理；客户端完成首次绑定与登录；备份有恢复验证记录。

## 2 部署前准备

### 2.1 环境与交付物

以 Ubuntu、systemd、Caddy 为主要路线。已有 Nginx 的环境可采用 deploy/nginx-auth.conf.example；不要在同一 IP 和端口上重复启动两个代理。

| 项目 | 准备要求 |
| --- | --- |
| 运行时 | 项目要求 Node.js 22.12.0 或以上及 npm；使用企业批准且仍受支持的版本 |
| 服务账户 | 独立 Linux 账户 remixauth；与桌面端 admin 账号分别管理 |
| HTTPS 地址 | 预先确定固定的 HTTPS 根地址，例如 https://auth.example.com |
| 域名与证书 | 域名解析到目标服务器，证书可信且主机名或 IP 匹配 |
| 网络 | 开放 HTTPS 所需端口，保留证书申请续期所需网络；3080 不向公网开放 |
| 服务交付物 | 当前版本编译的 dist-server、package.json、package-lock.json、deploy 目录 |
| 客户端 | 1.0.27 EXE，分发前核对 SHA256 |
| 数据边界 | 单实例运行，不允许多个进程写同一账号数据目录 |

运行时与代理的安装方式按目标系统软件源和企业策略确定。安装后执行下列命令；如 node 不在 /usr/bin/node，必须修改后续服务单元中的 ExecStart。

~~~bash
node --version
npm --version
command -v node
caddy version
~~~

## 3 准备服务器部署包

在干净、独立的源码目录中编译，避免混入旧 dist-server 内容。不要打包员工应用数据、密码文件或供应商密钥。在 Windows PowerShell 中进入项目目录执行，任一步失败先处理原因：

~~~powershell
npm ci
if ($LASTEXITCODE -ne 0) { throw '依赖安装失败，停止编译' }
npm run build:auth
if ($LASTEXITCODE -ne 0) { throw '授权服务编译失败，停止打包' }
Test-Path '.\dist-server\server\main.js'
tar -czf '.\auth-service-1.0.27.tar.gz' dist-server deploy package.json package-lock.json
if ($LASTEXITCODE -ne 0) { throw '部署包生成失败' }
Get-FileHash '.\auth-service-1.0.27.tar.gz' -Algorithm SHA256
~~~

记录哈希，通过企业批准的传输工具上传。以下以 /tmp/auth-service-1.0.27.tar.gz 为例，核对服务器计算值与 Windows 一致后解压：

~~~bash
sha256sum /tmp/auth-service-1.0.27.tar.gz
mkdir -p /tmp/video-remix-auth-1.0.27
tar -xzf /tmp/auth-service-1.0.27.tar.gz -C /tmp/video-remix-auth-1.0.27
test -f /tmp/video-remix-auth-1.0.27/dist-server/server/main.js
~~~

需要重建客户端时使用 npm run dist:win。REMIX_AUTH_URL 只决定旧固定地址版升级时的兼容地址，新安装仍须在向导填写服务器地址。仅部署授权服务不需要构建或启动前端。

## 4 首次部署账号服务

本节只用于首次部署。已有账号库的服务器按第 9 节升级，不要覆盖数据目录或重新初始化管理员。

### 4.1 创建账户与目录

~~~bash
getent passwd remixauth || sudo useradd --system --home-dir /var/lib/video-remix-auth --no-create-home --shell /usr/sbin/nologin remixauth
sudo install -d -o root -g root -m 0755 /opt/video-remix-auth
sudo install -d -o remixauth -g remixauth -m 0700 /var/lib/video-remix-auth
sudo install -d -o root -g remixauth -m 0750 /etc/video-remix-auth
sudo install -d -o root -g root -m 0700 /var/backups/video-remix-auth
sudo cp -a /tmp/video-remix-auth-1.0.27/dist-server /opt/video-remix-auth/
sudo install -o root -g root -m 0644 /tmp/video-remix-auth-1.0.27/package.json /opt/video-remix-auth/package.json
sudo install -o root -g root -m 0644 /tmp/video-remix-auth-1.0.27/package-lock.json /opt/video-remix-auth/package-lock.json
sudo npm ci --prefix /opt/video-remix-auth --omit=dev --omit=optional --ignore-scripts --no-audit --no-fund
~~~

任一命令失败应先处理原因。服务器仅安装生产依赖，跳过 Electron 安装脚本与可选原生依赖，使用项目 sql.js 持久化 SQLite。程序目录由 root 管理，服务账户只需写数据目录。

### 4.2 设置初始管理员密码

在服务器 Bash 中交互输入 8 至 128 位密码，不把真实密码直接写进命令、文档或截图。建议使用密码管理器生成并保管密码。下列命令只在输入长度合格时写入：

~~~bash
sudo -v
read -r -s -p '设置初始管理员密码: ' initial_password
printf '\n'
password_length=$(printf '%s' "$initial_password" | wc -m)
if [ "$password_length" -ge 8 ] && [ "$password_length" -le 128 ]; then
  printf '%s' "$initial_password" | sudo tee /etc/video-remix-auth/admin-password >/dev/null
  sudo chown root:remixauth /etc/video-remix-auth/admin-password
  sudo chmod 0640 /etc/video-remix-auth/admin-password
else
  printf '密码长度不合格，未写入，请重新执行本步\n' >&2
fi
unset initial_password password_length
sudo -u remixauth test -r /etc/video-remix-auth/admin-password
~~~

只有数据库内没有账号时才会创建内置管理员，账号固定为 admin。已有数据库时，修改密码文件不会重置密码；应在客户端“账号管理”中重置。该文件不是日常改密入口。

### 4.3 配置并启动 systemd

~~~bash
sudo install -o root -g root -m 0644 /tmp/video-remix-auth-1.0.27/deploy/video-remix-auth.service /etc/systemd/system/video-remix-auth.service
sudo systemctl daemon-reload
sudo systemctl enable --now video-remix-auth.service
sudo systemctl is-active video-remix-auth.service
sudo journalctl -u video-remix-auth.service -n 60 --no-pager
curl --fail --max-time 10 http://127.0.0.1:3080/health
~~~

预期：服务 active，健康接口返回 {"success":true}。AUTH_PORT 默认 3080，AUTH_DATA_DIR 默认 ./auth-data；正式部署使用模板中的绝对目录 /var/lib/video-remix-auth。AUTH_ADMIN_PASSWORD_FILE 指向前述密码文件；可选 AUTH_ADMIN_NAME 只设置空库初始化时的管理员姓名。

模板设置了 remixauth 账户、UMask=0077、ProtectSystem=strict 和 ReadWritePaths。改变数据目录时同步修改 AUTH_DATA_DIR、目录权限和 ReadWritePaths，不能只改其中一项。

## 5 配置 HTTPS 入口

### 5.1 Caddy 路线

在现有 /etc/caddy/Caddyfile 中合并站点，保留其他站点及全局设置。新域名环境可参考下面结构；替换 auth.example.com，并由运维完成可信证书配置与续期安排：

~~~text
https://auth.example.com {
    request_body {
        max_size 1MB
    }
    reverse_proxy 127.0.0.1:3080 {
        header_up X-Real-IP {remote_host}
        flush_interval -1
    }
}
~~~

~~~bash
sudo caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
sudo systemctl reload caddy
sudo systemctl is-active caddy
sudo journalctl -u caddy -n 60 --no-pager
~~~

deploy/Caddyfile.auth.example 是现有纯 IP 站点模板，含固定 IP、default_sni 和 shortlived 证书配置，不能原样用于其他地址。延续现网时保留已验证配置；新纯 IP 环境应按目标 Caddy 版本和证书条件验证。首次安装要求系统信任证书，不应通过关闭校验处理证书问题。

### 5.2 已采用 Nginx 的环境

采用 deploy/nginx-auth.conf.example，替换域名及证书路径，确保 limit_req_zone 位于 http 上下文。代理覆盖 X-Real-IP，并转发至 127.0.0.1:3080；nginx -t 成功后重载。证书签发续期按目标环境配置，不与 Caddy 同时占用同一端口。

## 6 部署验收

### 6.1 无账号接口与网络检查

替换下列示例地址。在服务器和至少一台员工网络中的电脑检查公网 HTTPS，不添加 curl -k：

~~~bash
sudo systemctl is-active video-remix-auth.service
sudo ss -lntp | grep ':3080'
curl --fail --max-time 10 http://127.0.0.1:3080/health
curl -i --max-time 10 https://auth.example.com/health
curl -i --max-time 10 https://auth.example.com/v1/me
curl -i --max-time 10 https://auth.example.com/v1/providers
curl -i --max-time 10 https://auth.example.com/v1/business/probe
~~~

| 检查 | 预期结果 |
| --- | --- |
| 监听 | 127.0.0.1:3080，不能是 0.0.0.0:3080 |
| GET /health | HTTP 200；JSON success 为布尔值 true |
| 未登录 GET /v1/me | HTTP 401；success 为 false；errorCode 为 AUTH_REQUIRED |
| 退役业务路径 | /v1/providers 与 /v1/business/probe 返回 HTTP 404 |
| 公网 HTTPS | 无证书错误；两条安装探测路径直接返回上述 JSON，无重定向 |

健康接口只证明存活，不代替数据库和权限验收。服务另提供 POST /v1/login、POST /v1/logout、GET /v1/users，以及 POST /v1/users/create、/status、/password、/delete；管理员在客户端维护账号，不需要另建浏览器后台。

### 6.2 用隔离账号验收权限

使用可清理的临时成员和测试设备，避免停用真实员工账号触发其配置清理。管理员登录客户端后按表验收并登记实际结果：

| 场景 | 合格标准 |
| --- | --- |
| 管理员 | admin 能登录并显示“账号管理”，可创建临时成员和管理员 |
| 成员权限 | 无账号管理菜单；直接调用账号管理接口返回 HTTP 403 |
| 内置保护 | 不能停用或删除内置 admin 及当前登录账号 |
| 停用 | 成员原会话失效，客户端收到明确停用响应后清理三类 API 配置 |
| 重新启用 | 可重新登录；已清除的 Key 不自动恢复；历史和素材保留 |
| 重置密码 | 原会话失效；旧密码不能登录，新密码能登录；API 配置保留 |
| 删除 | 账号不能再登录，原会话失效；本地业务历史不随账号删除 |
| 退出与重启 | 退出后旧会话不可继续使用；服务重启后客户端重新登录 |

停用清理需要配套服务端协议及新客户端。配置由当前 Windows 用户共享，停用成员时会清除该用户环境中的共用 API 配置。服务器不能立即擦除关机、离线或不运行的客户端，不能撤销供应商侧的真实 Key。

默认会话有效期为 12 小时，令牌只存在于服务进程内存中；重启会使会话失效。不要对当前实现使用多进程负载均衡或多副本共同写库。

## 7 安装并绑定 1.0.27 客户端

### 7.1 首次安装

1. 核对 EXE 与 SHA256，启动向导并选择安装位置。
2. 在“绑定授权服务器”填写 HTTPS 根地址，例如 https://auth.example.com，不填写 /health、/v1、用户名、密码、查询参数或片段。
3. 点击下一步。安装器探测 /health 和未登录 /v1/me，每次探测超时 8 秒；证书错误、重定向、超时或接口不符会阻止绑定。
4. 核对“绑定后无法在软件中修改服务器地址”的提示后确认，完成安装。
5. 启动软件，用服务器 admin 或分配的成员账号登录。正式远程版不在客户端初始化管理员。

绑定保存为当前 Windows 用户应用数据目录中的 auth-server-binding.json。首次安装不能静默跳过绑定；软件没有修改入口。绑定缺失或损坏时拒绝启动并提示重装，不自动回退默认服务器。

### 7.2 升级与更换地址

| 情况 | 1.0.27 行为 |
| --- | --- |
| 有效绑定后覆盖安装 | 保留绑定和 API 配置，不重复填地址 |
| 旧固定地址版直接升级 | 沿用构建时的兼容地址，本次预设为 https://114.132.186.95 |
| 已绑定而服务器离线 | 保留绑定，不因离线重新绑定 |
| 主动卸载 1.0.27 | 清除绑定、加密 API 配置、清理进度文件及对应临时文件，保留数据库与业务素材 |
| 卸载后重新安装 | 可重新填地址，三类 API 配置需要重填 |

升级内部卸载保留配置，不要为了普通升级主动卸载。确需换服务器，先备份本机业务资料并准备好重新配置的 Key，再使用 1.0.27 卸载程序卸载重装。旧版卸载程序不具备新清理规则，不能据此推断旧版卸载效果。

## 8 日常运维与备份恢复

### 8.1 常用检查

~~~bash
sudo systemctl status video-remix-auth.service --no-pager
sudo journalctl -u video-remix-auth.service -n 100 --no-pager
curl --fail --max-time 10 http://127.0.0.1:3080/health
sudo ls -ld /var/lib/video-remix-auth /var/lib/video-remix-auth/logs
~~~

服务日志在 /var/lib/video-remix-auth/logs。客户端通过“设置 → 系统设置 → 打开运行日志”取证。排查材料移除密码、Key、令牌及带敏感参数的链接。日志不能代替数据备份。

### 8.2 维护窗口内备份

sql.js 在进程内管理数据库，为获取一致副本，停止授权服务后备份。以下适用于前文目录及 Caddy 路线；备份含密码文件，目录仅 root 可访问，还应留一份受控异地副本。

~~~bash
backup_dir="/var/backups/video-remix-auth/manual-$(date -u +%Y%m%dT%H%M%SZ)"
sudo install -d -o root -g root -m 0700 "$backup_dir"
sudo systemctl stop video-remix-auth.service
sudo tar -czpf "$backup_dir/backup.tar.gz" -C / \
  opt/video-remix-auth var/lib/video-remix-auth etc/video-remix-auth \
  etc/systemd/system/video-remix-auth.service etc/caddy/Caddyfile
sudo tar -tzf "$backup_dir/backup.tar.gz" >/dev/null
sudo sha256sum "$backup_dir/backup.tar.gz"
sudo systemctl start video-remix-auth.service
sudo systemctl is-active video-remix-auth.service
~~~

tar 失败时先排查，明确备份无效，不继续升级。Nginx 环境把 Caddyfile 替换为实际代理配置；证书和代理状态目录按现网路径另行备份。记录备份哈希与恢复演练结果。

服务器备份不包含员工电脑中的历史、知识库和素材。员工业务库、独立素材目录、导出文件另行备份；加密接口配置不能当作可跨 Windows 用户和设备直接迁移的 Key 备份。

### 8.3 恢复原则

先在隔离目录或备用服务器解压检查，再进入恢复窗口。停止服务，保存故障现场，成套恢复匹配的代码、依赖、账号数据、配置和服务单元。不要只覆盖数据库，也不要让两个实例同时访问同一数据目录。

恢复后执行 daemon-reload、启动服务及第 6 节验收；恢复过代理配置则先校验再重载。所有客户端重新登录；回退数据可能回退账号停用状态及密码，须核对账号清单。备份需在隔离环境完成一次实际恢复和登录验证。

## 9 升级与回滚

1. 记录现有服务入口、代理配置、账号数量与状态；核对新包哈希，确认沿用原数据目录。
2. 按第 8 节停止服务并备份代码、依赖和完整数据，备份检查成功后进入下一步。
3. 在新的暂存目录准备新程序及生产依赖，确认入口存在；保留旧程序目录，不将新文件叠加到旧 dist-server。
4. 沿用账号目录和密码文件；无必要时不更改代理、地址或证书。登记来源版本、部署包哈希、时间与入口。
5. 启动后验收接口、权限及原有账号保留情况，用隔离成员验证停用协议，安排客户端重新登录。
6. 失败时停止新服务，保存失败日志和数据副本，恢复升级前匹配的代码、依赖与数据；复验后通知用户重新登录。

保持同一 HTTPS 地址可避免用户重新绑定。确需换地址，客户端按第 7 节迁移并重新填写 Key。

## 10 常见故障处理

| 现象 | 优先检查与处理 |
| --- | --- |
| 服务启动失败 | journal、node 路径、依赖、密码文件可读性与长度、数据目录权限 |
| 本机健康正常 公网失败 | 代理状态、防火墙、域名解析、证书匹配与有效期 |
| 安装验证失败 | HTTPS 根地址、两条探测接口的 JSON 和重定向、员工网络；不要关闭证书校验 |
| 升级仍连接原地址 | 保留绑定的预期行为；确需换地址应卸载重装 |
| 改密码文件无效 | 仅初始化空库；已有账号应在“账号管理”重置密码 |
| 重启要求登录 | 内存会话失效，重新登录；不要删除数据库 |
| 停用后 Key 消失 | 停用清理行为；重新启用后由成员重新填写 |
| 授权暂时不可达 | 恢复授权网络；不要靠删除绑定排障 |
| 误开多实例 | 停止并保留现场，恢复单实例，检查数据；不直接合并数据库 |
| API_RESET_FAILED | 检查客户端应用数据目录权限和清理错误，不删除业务库绕过 |

客户端新任务须校验授权，空闲约每 30 秒、运行任务约每 15 秒校验，窗口获得焦点也校验。只读身份查询临时失败会重试一次；已提交任务按最近一次成功授权起算最多 60 秒宽限，失败不续期。明确停用或会话失效会取消本机任务，发现时间仍含检查间隔与网络耗时；取消不代表供应商任务取消或退款。

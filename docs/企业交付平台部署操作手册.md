# 视频二创AI助手企业交付平台部署操作手册

文档版本：1.0　编写日期：2026年11月2日
适用代码：当前工作区 package.json 版本 1.0.19
交付对象：企业实施工程师、服务器运维人员、平台管理员、验收人员

本手册说明 Windows 桌面平台与集中账号鉴权服务的企业交付流程，覆盖服务器安装、HTTPS、管理员初始化、客户端集成、权限验收、备份恢复和升级回滚。执行顺序为服务端部署、HTTPS 验证、客户端构建安装、业务接口配置、联合验收和交接。示例域名、运行时版本和交付路径须按项目登记后替换。

## 1 适用范围与成功标准

### 1.1 平台组成和部署基线

平台为 Electron 桌面应用，集中部署的是账号鉴权服务，桌面程序安装在员工 Windows 设备。现有实现没有可直接部署供浏览器访问的业务 Web 平台。“平台账号”与 Linux 运维账号分别管理。

账号服务处理登录、身份和角色校验、账号创建与删除、停用与启用、密码重置、退出及相关运行日志。客户端直接请求模型、内容提取和图片生成供应商；业务数据库、公司知识库、历史记录、素材和接口配置保存在员工设备。

本手册的可执行基线为一台 Ubuntu 24.04 LTS 服务器、systemd、Nginx、域名 HTTPS，以及企业批准的 Node.js 24 LTS 补丁版本。项目实际最低要求为 Node 22.12.0；Node 24 是本手册选型。[R1]

按本文安装时排除可选原生依赖，服务使用 sql.js 读写 SQLite。服务只运行一个实例并监听 127.0.0.1:3080，不将多个进程指向同一数据库。客户端通过已有 dist:win 脚本生成 Windows x64 通用安装包，管理员和成员使用同一包。纯 IP 证书、其他代理和发行版需单独适配。

### 1.2 成功标准

服务开机自启；3080 只在回环地址监听；HTTPS 证书校验通过；空库只初始化一个内置管理员；管理员可以维护账号，成员调用管理接口返回 403；停用、密码重置、删除和退出能撤销原会话；客户端连接指定鉴权地址，完成真实业务并能重启读取本地资料；备份可恢复，代码可回滚。第 11 章逐项记录实际结果后方可签收。

本文提供待执行的部署与验收步骤，不代表已在目标企业环境执行。适用代码版本为 1.0.19；现网地址、现网版本和已部署能力须以企业实际部署清单为准，不沿用历史文档中的验收结论。

## 2 架构和交付前准备

### 2.1 网络和数据流

~~~text
员工 Windows 设备
  桌面客户端 ── HTTPS 443 ── Nginx
                                  │ 回环 HTTP 3080
                                  ▼
                            Node 账号鉴权服务
                                  │ 单实例读写
                                  ▼
                            SQLite 账号数据库

  桌面客户端 ── HTTPS ── 批准的模型及内容供应商
  桌面客户端 ── 本地磁盘 ── 知识库 历史记录 素材 加密配置
~~~

登录令牌保存在内存中；客户端调用 /v1/me 校验身份，账号管理接口由服务端检查 admin 角色。普通鉴权请求默认超时约 5 秒；空闲会话默认约 30 秒校验一次，任务期间默认约 1 秒校验一次，发现停权的时间还包含网络耗时。服务会话固定默认有效 12 小时，当前启动入口没有提供调整时长的环境变量。客户端或服务重启后需要重新登录。

### 2.2 前置检查

1. 准备支持 systemd 的服务器、sudo 权限、可用 DNS、时间同步、证书申请条件和备份存储。可从 2 vCPU、2 GB 内存、20 GB 可用磁盘起步；这是建议的部署起点，容量须按并发任务和登录频率实测。
2. 分配独立鉴权域名，A 记录指向服务器或入口代理；本文站点仅配置 IPv4；使用 AAAA 时须另加 IPv6 监听并实测，或移除无效 AAAA 记录。HTTP 证书验证需要公网能访问 80 端口。
3. 允许访问企业批准的 Ubuntu 软件源、Node 下载源、npm 镜像和证书服务。隔离网络提前导入同版本同架构运行时及依赖，不将 Windows node_modules 复制到 Linux。
4. 准备 Windows x64 构建机、受支持的 Node 和 npm、已确认的源码和 package-lock.json，以及 Electron 和 npm 依赖下载条件。
5. 登记已有站点、监听端口和安全组。已有 Nginx 或 Caddy 时先备份原配置，选用一个代理提供入口，避免同时占用 80、443。
6. 登记维护窗口、故障联系人和回退责任人。若企业要求 MFA、AD、LDAP、OIDC、SAML、集中业务数据或不可抵赖审计，须单独评估集成；当前账号服务没有这些现成配置项。

### 2.4 网络要求

| 方向 | 端口或目标 | 用途和验证 |
| --- | --- | --- |
| 运维入站 | SSH 实际端口 | 仅运维网段 保留既有访问 |
| 业务入站 | TCP 443 | 客户端鉴权和健康检查 |
| 证书入站 | TCP 80 | ACME HTTP 验证和跳转 |
| 本机监听 | 127.0.0.1:3080 | 只允许回环代理访问 |
| 服务端出站 | DNS HTTPS NTP | 解析 依赖 证书 校时 |
| 员工设备出站 | 鉴权域名及批准的供应商 | 鉴权和业务直连 |

网络策略由企业现有防火墙和安全组实施。不要直接启用未知的默认防火墙策略，以免中断 SSH 或其他站点。上线须同时核查主机监听与外部访问，不能只查看安全组配置。

## 3 构建和校验服务端交付包

### 3.1 构建账号服务

在 Windows 构建机用 PowerShell 进入项目根目录。先登记源码版本及本地改动，再执行项目已有脚本。这些命令不会启动前端服务。

~~~powershell
$OutputEncoding = [Console]::OutputEncoding = [System.Text.UTF8Encoding]::new()
node --version
npm --version
git rev-parse HEAD
git status --short
npm ci
if ($LASTEXITCODE -ne 0) { throw '依赖安装失败' }
npm run typecheck
if ($LASTEXITCODE -ne 0) { throw '类型检查失败' }
npm test
if ($LASTEXITCODE -ne 0) { throw '自动化测试失败' }
if (Test-Path -LiteralPath .\dist-server) {
  $taskOldBuild = Join-Path $PWD ('dist-server-before-delivery-' +
    (Get-Date -Format 'yyyyMMddHHmmss'))
  if (Test-Path -LiteralPath $taskOldBuild) { throw '旧构建备份路径已存在' }
  Move-Item -LiteralPath .\dist-server -Destination $taskOldBuild
}
npm run build:auth
if ($LASTEXITCODE -ne 0) { throw '账号服务编译失败' }
Test-Path .\dist-server\server\main.js
~~~

验证方式：各命令以 0 退出，main.js 存在。构建前将已有 dist-server 移到备份目录，确保交付输出不夹带已退役文件。测试数量取实际输出，不使用历史测试数。若发布包含本地修改，须交付对应源码快照或补丁，不能只登记 Git 提交号。

### 3.2 打包和上传

用全新目录生成包。目录或压缩包已存在时先停止检查，防止混入旧文件。不复制旧业务代理、员工业务资料或服务器账号数据库。

~~~powershell
$taskVersion = (Get-Content -LiteralPath .\package.json -Encoding UTF8 |
  ConvertFrom-Json).version
$taskStage = Join-Path $PWD "delivery-auth-$taskVersion"
$taskZip = "$taskStage.zip"
if ((Test-Path -LiteralPath $taskStage) -or
    (Test-Path -LiteralPath $taskZip)) { throw '交付路径已存在' }
New-Item -ItemType Directory -Path $taskStage | Out-Null
Copy-Item -LiteralPath .\dist-server -Destination $taskStage -Recurse
Copy-Item -LiteralPath .\deploy -Destination $taskStage -Recurse
Copy-Item -LiteralPath .\package.json, .\package-lock.json -Destination $taskStage
Compress-Archive -Path "$taskStage\*" -DestinationPath $taskZip
Get-FileHash -LiteralPath $taskZip -Algorithm SHA256
~~~

通过批准的 SFTP 或制品库上传到 /srv/remix-delivery。可信交付清单应包含 SHA256、应用版本、源码记录、构建时间、Node/npm 版本。服务器执行 sha256sum，将结果与可信清单逐字比对；校验一致后才解压。

## 4 准备 Linux 服务器和运行时

### 4.1 初装检查

本章及第 5、6 章 Bash 命令在同一 root 会话执行。已有服务升级从第 13 章开始，不重新初始化数据库。

~~~bash
sudo -i
set -euo pipefail
cat /etc/os-release
uname -m
timedatectl status
ss -lntp
systemctl status video-remix-auth --no-pager || true
~~~

预期结果：系统和架构符合选型，时间同步正常，端口无冲突。发现运行中的同名服务或已有账号数据时，先确认现网状态，转入升级流程。

### 4.2 安装基础软件

~~~bash
apt-get update
apt-get install -y ca-certificates curl xz-utils unzip nginx certbot
nginx -t
systemctl enable --now nginx
~~~

软件源须符合企业补丁策略。nginx -t 失败时先排查已有配置，不继续加载新站点。企业统一提供证书工具时使用批准的安装方式，不重复安装多个 Certbot 实例。

### 4.3 安装固定版本 Node

企业可以预置符合要求的运行时。以下示例从官方下载并固定安装，输入审批通过的完整 Node 24 补丁版本；不以“最新版本”作为可重复交付依据。[R1]

~~~bash
install -d -m 0755 /srv/remix-delivery/runtime
cd /srv/remix-delivery/runtime
read -r -p '输入批准的完整 Node 版本 如 v24.数字.数字: ' NODE_VERSION
[[ "$NODE_VERSION" =~ ^v24\.[0-9]+\.[0-9]+$ ]]
case "$(uname -m)" in
  x86_64) NODE_ARCH=x64 ;;
  aarch64) NODE_ARCH=arm64 ;;
  *) echo '服务器架构不在本文基线内'; exit 1 ;;
esac
NODE_DIST="node-${NODE_VERSION}-linux-${NODE_ARCH}"
NODE_BASE="https://nodejs.org/dist/${NODE_VERSION}"
curl --fail --show-error --location --remote-name \
  "$NODE_BASE/$NODE_DIST.tar.xz"
curl --fail --show-error --location --remote-name \
  "$NODE_BASE/SHASUMS256.txt"
grep -F "  $NODE_DIST.tar.xz" SHASUMS256.txt | sha256sum -c -
test ! -e "/opt/$NODE_DIST"
test ! -e /opt/node-remix
test ! -L /opt/node-remix
tar -xJf "$NODE_DIST.tar.xz" -C /opt
ln -s "/opt/$NODE_DIST" /opt/node-remix
/opt/node-remix/bin/node --version
PATH=/opt/node-remix/bin:/usr/bin:/bin /opt/node-remix/bin/npm --version
~~~

验证方式：版本与审批记录一致，摘要检查显示 OK，node 和 npm 可执行。摘要文件和安装包来自官方或批准的镜像；需要签名验证时按企业运行时引入流程完成。已有 /opt/node-remix 时核对并复用或独立升级，不执行覆盖安装。

### 4.4 建立服务账号和目录

~~~bash
id remixauth >/dev/null 2>&1 || useradd \
  --system --user-group --home-dir /var/lib/video-remix-auth \
  --no-create-home --shell /usr/sbin/nologin remixauth
install -d -o root -g root -m 0755 /opt/video-remix-auth
install -d -o remixauth -g remixauth -m 0700 /var/lib/video-remix-auth
install -d -o root -g remixauth -m 0750 /etc/video-remix-auth
install -d -o root -g root -m 0700 /var/backups/video-remix-auth
~~~

预期结果：服务账号不可交互登录，程序由 root 管理，数据目录仅 remixauth 可访问。remixauth 不作为员工登录平台的账号。

## 5 安装和配置账号鉴权服务

### 5.1 安装交付物和依赖

输入已核验 SHA256 的服务端包路径。程序目录必须为空；已有部署使用升级流程。

~~~bash
read -r -p '输入已校验的服务端 zip 绝对路径: ' DEPLOY_ZIP
test -f "$DEPLOY_ZIP"
test -z "$(find /opt/video-remix-auth -mindepth 1 -maxdepth 1 -print -quit)"
unzip -q "$DEPLOY_ZIP" -d /opt/video-remix-auth
cd /opt/video-remix-auth
test -f dist-server/server/main.js
test -f package-lock.json
PATH=/opt/node-remix/bin:/usr/bin:/bin /opt/node-remix/bin/npm ci \
  --omit=dev --omit=optional --ignore-scripts --no-audit --no-fund
/opt/node-remix/bin/node -e \
  "console.log(require('./package.json').version); require('sql.js')().then(() => console.log('sql.js ready')).catch(() => process.exit(1))"
chown -R root:root /opt/video-remix-auth
~~~

预期结果：版本正确，输出 sql.js ready。--ignore-scripts 跳过桌面相关安装脚本；--omit=optional 排除 better-sqlite3，使服务走本文的 sql.js 路径。该命令仍安装清单中的其他生产依赖，不代表服务包已经专门裁剪。

### 5.2 设置首次管理员密码

内置用户名固定为 admin，AUTH_ADMIN_NAME 只设置显示名称。代码限制密码长度为 8 至 128 位；建议企业采用至少 16 位独立生成密码，并满足企业密码策略。通过安全输入设置，不把真实密码写入命令或交付资料。

~~~bash
test ! -e /var/lib/video-remix-auth/video-remix-history.sqlite
read -r -s -p '输入初始管理员密码: ' ADMIN_PASSWORD
printf '\n'
test "${#ADMIN_PASSWORD}" -ge 8
test "${#ADMIN_PASSWORD}" -le 128
install -o root -g remixauth -m 0640 /dev/null \
  /etc/video-remix-auth/admin-password
printf '%s' "$ADMIN_PASSWORD" > /etc/video-remix-auth/admin-password
unset ADMIN_PASSWORD
stat -c '%U %G %a %n' /etc/video-remix-auth/admin-password
~~~

预期结果：文件归 root:remixauth 所有、权限 640，不 cat 密码文件。该文件仅在空账号库时初始化 admin；修改它不会重置已有密码。当前入口每次启动仍读取已配置的密码文件，因此保留其可读性，不在保留环境变量的情况下直接删除文件。

### 5.3 配置 systemd

使用已有 deploy/video-remix-auth.service 模板，将 Node 改为第 4 章的绝对路径。模板启用系统目录只读、私有临时目录和仅数据目录可写等限制。[R5]

~~~bash
install -o root -g root -m 0644 \
  /opt/video-remix-auth/deploy/video-remix-auth.service \
  /etc/systemd/system/video-remix-auth.service
sed -i 's|ExecStart=/usr/bin/node |ExecStart=/opt/node-remix/bin/node |' \
  /etc/systemd/system/video-remix-auth.service
install -d -m 0755 /etc/systemd/system/video-remix-auth.service.d
cat > /etc/systemd/system/video-remix-auth.service.d/enterprise.conf <<'EOF'
[Service]
Environment="AUTH_ADMIN_NAME=企业管理员"
Environment="PATH=/opt/node-remix/bin:/usr/bin:/bin"
EOF
systemd-analyze verify /etc/systemd/system/video-remix-auth.service
systemctl daemon-reload
systemctl enable --now video-remix-auth
systemctl is-active video-remix-auth
systemctl cat video-remix-auth
~~~

当前入口接收四项环境变量：AUTH_PORT，默认 3080；AUTH_DATA_DIR，持久化目录；AUTH_ADMIN_PASSWORD_FILE，初始密码文件；AUTH_ADMIN_NAME，首次管理员显示名称。不要添加没有实现的 JWT_SECRET、DATABASE_URL、REDIS_URL、SESSION_TTL 或 AUTH_HOST。

### 5.4 验证本机服务

~~~bash
curl --fail --silent --show-error --retry 10 --retry-connrefused \
  --retry-delay 1 --max-time 5 http://127.0.0.1:3080/health
ss -lntp | grep ':3080'
systemctl status video-remix-auth --no-pager
journalctl -u video-remix-auth -n 50 --no-pager
stat -c '%U %G %a %n' /var/lib/video-remix-auth
~~~

预期结果：HTTP 200 且返回 {"success":true}；监听 127.0.0.1:3080，不是 0.0.0.0 或公网地址；服务 active，数据目录权限 700。数据库为该目录中的 video-remix-history.sqlite。首次启动记录 auth.admin-initialized 和 auth.ready；升级不应再次初始化管理员。

排除 better-sqlite3 后可能出现 database.engine-fallback 日志。随后 sql.js 加载正常且健康检查通过时，这是本文预期的引擎回退；若服务退出或没有 auth.ready，仍按故障处理。

## 6 配置 HTTPS 和反向代理

### 6.1 配置证书申请前的 HTTP 站点

以下基线为独立域名、标准 Ubuntu Nginx sites-enabled 结构。已有业务须先备份并合并，不覆盖其他站点。输入企业域名和证书通知邮箱。

~~~bash
read -r -p '输入鉴权域名: ' AUTH_DOMAIN
read -r -p '输入证书通知邮箱: ' ACME_EMAIL
[[ "$AUTH_DOMAIN" =~ ^[A-Za-z0-9.-]+$ ]]
getent ahosts "$AUTH_DOMAIN"
nginx -T > /root/nginx-before-remix-$(date -u +%Y%m%dT%H%M%SZ).txt 2>&1
install -d -m 0755 /var/www/remix-auth-acme
test ! -e /etc/nginx/sites-available/video-remix-auth
test ! -e /etc/nginx/sites-enabled/video-remix-auth
cat > /etc/nginx/sites-available/video-remix-auth <<'EOF'
server {
    listen 80;
    server_name AUTH_DOMAIN_PLACEHOLDER;
    location ^~ /.well-known/acme-challenge/ {
        root /var/www/remix-auth-acme;
        default_type text/plain;
    }
    location / { return 404; }
}
EOF
sed -i "s/AUTH_DOMAIN_PLACEHOLDER/$AUTH_DOMAIN/g" \
  /etc/nginx/sites-available/video-remix-auth
ln -s /etc/nginx/sites-available/video-remix-auth \
  /etc/nginx/sites-enabled/video-remix-auth
nginx -t
systemctl reload nginx
~~~

从外部设备请求该域名的 HTTP，确认流量落到本机；临时站点普通路径返回 404 属于预期。负载均衡需将 ACME 路径转到此 webroot；不能公网 HTTP 验证时改用企业证书或 DNS 验证流程。

### 6.2 申请域名证书

~~~bash
certbot certonly --webroot -w /var/www/remix-auth-acme \
  -d "$AUTH_DOMAIN" --email "$ACME_EMAIL" \
  --agree-tos --non-interactive
certbot certificates
~~~

预期结果：证书 SAN、有效期正确，存在 fullchain.pem 和 privkey.pem。下一步使用 /etc/letsencrypt/live/域名/ 下的路径；若输出为带后缀的其他证书名称，必须替换为实际路径。[R4]

### 6.3 启用 HTTPS 站点

保留 ACME 路径，并对登录限流。limit_req_zone 必须位于 http 上下文；标准 Ubuntu 的 sites-enabled 从 http 引入，因此可放在站点文件顶层。企业结构不同时先调整上下文。[R2][R3]

~~~bash
cp -a /etc/nginx/sites-available/video-remix-auth \
  /root/video-remix-auth-http-$(date -u +%Y%m%dT%H%M%SZ).conf

limit_req_zone $binary_remote_addr zone=remix_auth_login:10m rate=5r/m;
~~~

验证方式：nginx -t 成功；外部 HTTPS 证书校验通过并返回 {"success":true}；HTTP 普通路径跳转到 HTTPS。不用 curl -k、关闭 TLS 校验或 Electron 安全开关作为验收手段。

Nginx 必须覆盖 X-Real-IP；后台只信任回环代理传入的有效 IP。前面还有负载均衡时，此配置看到的是负载均衡地址，限流可能集中在该地址；上线前由网络团队按实际拓扑设置可信代理链并验证来源。示例登录限流平均每来源每分钟 5 次、突发 5 次；企业统一出口会共享来源配额，须实测调整。

## 7 验证账号接口和管理员初始化

### 7.1 真实接口清单

| 方法和路径 | 权限 | 输入或用途 |
| --- | --- | --- |
| GET /health | 无需登录 | 返回 success |
| POST /v1/login | 无需登录 | username password 返回 token 和 user |
| GET /v1/me | 已登录 | 返回当前 user |
| POST /v1/logout | 已登录 | JSON 空对象 撤销当前会话 |
| GET /v1/users | 管理员 | 返回 users |
| POST /v1/users/create | 管理员 | username password displayName role |
| POST /v1/users/status | 管理员 | userId active 布尔值 |
| POST /v1/users/password | 管理员 | userId password 撤销全部会话 |
| POST /v1/users/delete | 管理员 | userId 删除并撤销全部会话 |

JSON 为 UTF-8，正文上限 16 KiB；代理的 1 MB 限制不会扩大后端限制。路径严格匹配，不增加末尾斜杠、查询参数或业务子路径。除登录和健康接口外，设置 Authorization: Bearer 加登录令牌。该令牌不是 JWT，不需配置签名密钥。

### 7.2 管理员登录和身份验证

Windows 验收设备使用 PowerShell，替换域名，通过凭据提示输入密码。验收时不录制包含凭据或令牌的终端会话。

~~~powershell
$OutputEncoding = [Console]::OutputEncoding = [System.Text.UTF8Encoding]::new()
$authBase = 'https://auth.example.com'
$adminCredential = Get-Credential -UserName 'admin' -Message '输入管理员凭据'
$adminBody = @{
  username = $adminCredential.UserName
  password = $adminCredential.GetNetworkCredential().Password
} | ConvertTo-Json -Compress
try {
  $adminLogin = Invoke-RestMethod -Method Post -Uri "$authBase/v1/login" `
    -ContentType 'application/json; charset=utf-8' `
    -Body ([System.Text.Encoding]::UTF8.GetBytes($adminBody))
} finally {
  Remove-Variable adminBody, adminCredential -ErrorAction SilentlyContinue
}
if (-not $adminLogin.success -or $adminLogin.user.role -ne 'admin') {
  throw '管理员登录或角色校验失败'
}
$adminHeaders = @{ Authorization = "Bearer $($adminLogin.token)" }
Invoke-RestMethod -Uri "$authBase/v1/me" -Headers $adminHeaders |
  Select-Object success, user
Invoke-RestMethod -Uri "$authBase/v1/users" -Headers $adminHeaders |
  Select-Object success, users
~~~

预期结果：success=true，username=admin、role=admin、isActive=true。首次用户列表仅有内置管理员；已有环境与升级前账号清单比较，不要求只有一个用户。不要直接输出 adminLogin 对象，以免显示 token。

完成本章接口验收后、正式交接前，由企业管理员在客户端“账号管理”中立即重置 admin 密码并受控保管。若已提前重置，先重新执行本节登录命令获取新的管理员令牌，再继续后续接口验收。重置自身密码会退出，须用新密码重新登录。初始密码文件不会随之更新，也不能作为当前密码的证明。

### 7.3 创建验收成员并验证权限

正式账号可在客户端“账号管理 → 新增账号”创建。账号为 3 至 50 位字母、数字、下划线、点或短横线，姓名为 1 至 100 字，角色为 admin 或 member，密码为 8 至 128 位。下面在同一 PowerShell 会话创建专用临时账号，不使用真实员工账号做删除、停用或密码重置测试。

~~~powershell
$acceptUsername = 'accept_' + (Get-Date -Format 'yyyyMMddHHmmss')
$acceptCredential = Get-Credential -UserName $acceptUsername `
  -Message '设置临时成员密码 8至128位'
$createBody = @{
  username = $acceptUsername
  displayName = '交付验收临时成员'
  password = $acceptCredential.GetNetworkCredential().Password
  role = 'member'
} | ConvertTo-Json -Compress
try {
  $created = Invoke-RestMethod -Method Post -Uri "$authBase/v1/users/create" `
    -Headers $adminHeaders -ContentType 'application/json; charset=utf-8' `
    -Body ([System.Text.Encoding]::UTF8.GetBytes($createBody))
  $acceptUserId = $created.user.id
  if (-not $created.success -or -not $acceptUserId) { throw '创建失败' }
  $memberBody = @{
    username = $acceptUsername
    password = $acceptCredential.GetNetworkCredential().Password
  } | ConvertTo-Json -Compress
  $memberLogin = Invoke-RestMethod -Method Post -Uri "$authBase/v1/login" `
    -ContentType 'application/json; charset=utf-8' `
    -Body ([System.Text.Encoding]::UTF8.GetBytes($memberBody))
} finally {
  Remove-Variable createBody, memberBody, acceptCredential `
    -ErrorAction SilentlyContinue
}
$memberHeaders = @{ Authorization = "Bearer $($memberLogin.token)" }
Invoke-RestMethod -Uri "$authBase/v1/me" -Headers $memberHeaders |
  Select-Object success, user
try {
  Invoke-RestMethod -Uri "$authBase/v1/users" -Headers $memberHeaders |
    Out-Null
  throw '权限验收失败 成员能够访问用户列表'
} catch {
  if ([int]$_.Exception.Response.StatusCode -ne 403) { throw }
  Write-Output '成员管理权限验收通过 HTTP 403'
}
~~~

预期结果：成员登录及 /v1/me 成功，角色为 member；用户列表返回 403。账号区分大小写，不将不同大小写账号当成同一员工。权限拒绝须来自服务器，只隐藏客户端按钮不能作为证据。

### 7.4 停用和会话撤销

沿用上一节临时账号。停用撤销该用户全部会话；重新启用不会恢复旧令牌。

~~~powershell
$statusBody = @{ userId = $acceptUserId; active = $false } |
  ConvertTo-Json -Compress
Invoke-RestMethod -Method Post -Uri "$authBase/v1/users/status" `
  -Headers $adminHeaders -ContentType 'application/json; charset=utf-8' `
  -Body $statusBody | Select-Object success
try {
  Invoke-RestMethod -Uri "$authBase/v1/me" -Headers $memberHeaders |
    Out-Null
  throw '撤销失败 停用后旧会话仍可用'
} catch {
  if ([int]$_.Exception.Response.StatusCode -ne 401) { throw }
  Write-Output '停用会话撤销验收通过 HTTP 401'
}
$statusBody = @{ userId = $acceptUserId; active = $true } |
  ConvertTo-Json -Compress
Invoke-RestMethod -Method Post -Uri "$authBase/v1/users/status" `
  -Headers $adminHeaders -ContentType 'application/json; charset=utf-8' `
  -Body $statusBody | Select-Object success
~~~

另用两台客户端登录临时成员，重复停用，检查空闲界面和在途任务都能发现失效，记录实际时延。内置 admin 和当前管理员受到保护，不能停用或删除。

### 7.5 密码重置和账号删除

启用后用原密码重新登录临时成员，并在第二台客户端登录同一成员。管理员进入“账号管理 → 重置密码”，输入新密码并确认。预期旧密码失败、所有旧会话失效、新密码可登录。不通过修改初始密码文件重置已有账号。

接口重置方法如下，userId 沿用临时账号：

~~~powershell
$newCredential = Get-Credential -UserName $acceptUsername `
  -Message '设置临时成员的新密码'
$resetBody = @{
  userId = $acceptUserId
  password = $newCredential.GetNetworkCredential().Password
} | ConvertTo-Json -Compress
try {
  Invoke-RestMethod -Method Post -Uri "$authBase/v1/users/password" `
    -Headers $adminHeaders -ContentType 'application/json; charset=utf-8' `
    -Body ([System.Text.Encoding]::UTF8.GetBytes($resetBody)) |
    Select-Object success
} finally {
  Remove-Variable newCredential, resetBody -ErrorAction SilentlyContinue
}
~~~

完成客户端和第 11 章验收后删除临时账号，确认列表移除、旧会话不可用且无法登录。正式删除前按企业流程确认对象。删除平台账号不等于回收员工设备资料或供应商密钥。

~~~powershell
$deleteBody = @{ userId = $acceptUserId } | ConvertTo-Json -Compress
Invoke-RestMethod -Method Post -Uri "$authBase/v1/users/delete" `
  -Headers $adminHeaders -ContentType 'application/json; charset=utf-8' `
  -Body $deleteBody | Select-Object success
Invoke-RestMethod -Method Post -Uri "$authBase/v1/logout" `
  -Headers $adminHeaders -ContentType 'application/json' -Body '{}' |
  Select-Object success
Remove-Variable adminLogin, adminHeaders, memberLogin, memberHeaders `
  -ErrorAction SilentlyContinue
~~~

### 7.6 限流和会话规则

后端默认对单来源每 15 分钟最多 60 次登录请求、单来源与用户名组合每 15 分钟最多 10 次失败尝试限流。成功清除对应失败组合计数，不清除来源请求计数；触发可能返回 429。不要在生产反复撞密码测试，使用批准的环境与独立出口。

服务端使用随机令牌，内存保存令牌哈希和会话信息，重启会撤销全部会话。默认会话为固定 12 小时，身份校验不会自动续期；当前没有多副本共享会话配置。

## 8 构建并安装远程鉴权客户端

### 8.1 写入企业地址和生成安装包

1.0.27 起，新安装通过安装向导填写并验证鉴权服务器的 HTTPS 根地址，不带账号密码、查询参数、片段或 /v1、/auth 等子路径。确认后固化至本机，覆盖升级保留绑定；断网不会解锁。更换地址需要主动卸载后重装，卸载同时清除本机 API 配置并保留业务资料。

dist-electron/auth-config.json 中的 url 仅用于旧固定地址安装的升级兼容。旧版曾使用其他地址时，须将 REMIX_AUTH_URL 设为其原地址；新安装仍在向导中输入地址，运行时环境变量不会修改已有绑定。在 Windows 构建机项目根目录执行：

~~~powershell
$previousAuthUrl = $env:REMIX_AUTH_URL
try {
  $env:REMIX_AUTH_URL = 'https://auth.example.com'
  npm run dist:win
  if ($LASTEXITCODE -ne 0) { throw '通用安装包构建失败' }
} finally {
  $env:REMIX_AUTH_URL = $previousAuthUrl
}
Get-Content -LiteralPath .\dist-electron\auth-config.json -Encoding UTF8
$taskVersion = (Get-Content -LiteralPath .\package.json -Encoding UTF8 |
  ConvertFrom-Json).version
$taskInstaller = Join-Path $PWD `
  "release\video-remix-universal-setup-$taskVersion.exe"
if (-not (Test-Path -LiteralPath $taskInstaller)) { throw '未找到安装包' }
Get-FileHash -LiteralPath $taskInstaller -Algorithm SHA256
Get-AuthenticodeSignature -LiteralPath $taskInstaller |
  Select-Object Status, SignerCertificate
~~~

预期结果：退出码为 0、URL 正确、安装包存在并记录 SHA256。按当前版本，文件名为 video-remix-universal-setup-1.0.19.exe，实际以 package.json 为准。

dist:win 使用 electron-builder.universal.cjs，替换远程鉴权入口、写入 authMode=remote，并启用已有 ASAR 完整性配置。不能仅手改 package.json 的 authMode 视为完成集成。普通 build 会重新生成桌面产物，正式交付须使用完整 dist:win 生成的包。

当前构建配置未完成企业代码签名配置，状态以实际检查为准。企业要求签名时先接入批准的签名和验证流程，再分发；不要求员工关闭系统安全防护。

### 8.2 安装和首次登录

1. 干净验收设备核对包摘要、版本及签名，确认鉴权网络、系统时间与企业证书策略。
2. 按企业软件分发流程安装并启动。首次应直接登录服务器账号，不要求员工初始化本机管理员；出现本机初始化流程时停止分发，核对构建方式。
3. 用 admin 登录，检查“账号管理”入口和用户列表，创建正式管理员和成员。避免多人共用 admin，角色由服务端决定。
4. 换成员登录，确认没有账号管理入口，并完成第 7 章服务端权限测试。
5. 第二台设备用同一成员登录，角色保持一致；新设备的本地知识库、历史和接口配置应为空，不期待服务端同步业务资料。
6. 完全退出重启，重新登录，确认业务资料在实际存储目录保留。远程会话和密码不写入本地账号库。

## 9 账号鉴权与平台业务整体集成

### 9.1 配置各设备业务接口

只部署账号服务尚不能完成创作，每台员工设备还需完成以下配置。

1. 设置页“API 接口配置”填写批准的模型地址、模型名称和 API Key，保存本设备配置。
2. 按启用的模块配置内容提取、图片生成供应商并执行界面连接测试。具体参数依照供应商合同和项目接入说明；不将鉴权 URL 当成模型或解析地址。
3. 在“存储地址”登记知识库和历史数据库位置，修改后按提示重启并检查迁移。独立设置的图文素材目录也需登记。
4. 用允许外发的素材完成提取、生成、历史保存和需要的导出，检查内容与实际供应商消耗。
5. 完全退出重启后重新登录，检查配置、历史和知识库保留；换设备须重新配置，不用本机加密文件做跨设备密钥分发。

接口配置经 Electron safeStorage 加密保存在本机 providers.encrypted。更换设备、操作系统用户或安全存储后原文件可能无法解密，应通过企业凭据渠道重新配置。更改业务存储目录不迁移设备密钥、日志与界面偏好。

### 9.2 验证授权闭环

客户端在需要授权的操作和任务执行中校验身份。停用、密码重置、删除或会话到期被发现后，撤销会话并取消任务、返回登录状态。

鉴权服务暂时不可达、超时或响应异常时，客户端保留内存会话状态，但拒绝当前授权操作并中断在途任务，后台继续校验。网络恢复且服务端会话仍有效时可以重试；服务曾重启则旧令牌失效，需重新登录。验收须区分网络故障和明确的账号失效。

服务器无法收回已导出的内容或复制的 Key，也不能保证阻止篡改客户端绕过本机限制。当前没有将创作请求统一代理到鉴权服务器的实现。企业要求付费 API 全部由服务器强制授权时，须另行设计业务代理与密钥管理，不能把本机直连验收为该能力。

### 9.3 核对数据和访问边界

同一设备及同一应用数据目录的知识库、历史和接口配置由本机使用，不提供按平台账号隔离的业务资料。多人共用设备应采用企业设备隔离或独立操作系统用户，并实际验证数据目录，不能以账号角色代替数据隔离。

账号服务器不接收模型 Key、提示词或创作内容；/v1/providers 和 /v1/business/* 应返回 404，不为这些路径恢复历史代理。供应商网络问题从员工设备排查，不将供应商连通性只验收在账号服务器上。


## 10 日常运维和备份恢复

### 10.1 监控和日志

至少监控 HTTPS 健康、服务状态、证书到期、磁盘空间、备份结果和 401/403/429/5xx 异常变化。/health 仅证明进程响应，不能代替登录、持久化和权限测试。

~~~bash
systemctl is-active video-remix-auth
curl --fail --silent --show-error https://auth.example.com/health
journalctl -u video-remix-auth -n 100 --no-pager
find /var/lib/video-remix-auth/logs -maxdepth 1 -type f -name '*.log'
df -h /var/lib/video-remix-auth /var/backups/video-remix-auth
certbot certificates
~~~

运行日志位于 /var/lib/video-remix-auth/logs，采用 JSON 行，可核对时间、事件、操作者、目标和错误码。当前默认约 5 MiB 每文件、最多 20 个文件并按 14 天清理，这是实现限制，不等于企业合规留存期。需要长期审计时接入企业日志采集，限制访问，不采集密码、令牌、请求正文或密钥。

### 10.2 一致性备份

sql.js 从内存写回数据库，本文采用停服务后备份完整目录的一致性方案。维护窗口内会短暂不可鉴权，服务恢复后旧会话失效。不要将运行中简单 cp 单个 SQLite 文件作为已验证的一致性备份。

在 root Bash 会话执行：

~~~bash
set -euo pipefail
BACKUP_ROOT=/var/backups/video-remix-auth
BACKUP_DIR="$BACKUP_ROOT/$(date -u +%Y%m%dT%H%M%SZ)"
install -d -o root -g root -m 0700 "$BACKUP_DIR"
systemctl stop video-remix-auth
trap 'systemctl start video-remix-auth' EXIT
cp -a /var/lib/video-remix-auth "$BACKUP_DIR/data"
cp -a /opt/video-remix-auth "$BACKUP_DIR/app"
cp -a /etc/video-remix-auth "$BACKUP_DIR/secrets"
cp -a /etc/systemd/system/video-remix-auth.service "$BACKUP_DIR/"
cp -a /etc/systemd/system/video-remix-auth.service.d "$BACKUP_DIR/"
cp -a /etc/nginx/sites-available/video-remix-auth "$BACKUP_DIR/nginx.conf"
systemctl cat video-remix-auth > "$BACKUP_DIR/service-effective.txt"
/opt/node-remix/bin/node --version > "$BACKUP_DIR/node-version.txt"
(cd "$BACKUP_DIR" && sha256sum data/video-remix-history.sqlite \
  > database.sha256)
systemctl start video-remix-auth
systemctl is-active video-remix-auth
curl --fail --silent --show-error --retry 10 --retry-connrefused \
  --retry-delay 1 --max-time 5 http://127.0.0.1:3080/health
trap - EXIT
printf '%s\n' "$BACKUP_DIR"
~~~

备份包含账号哈希、日志和初始密码文件，须按敏感资料限制访问并加密保存到异机。依照企业策略另行备份 /etc/letsencrypt 或企业证书，验证恢复路径，不把证书私钥放入普通交付包。建议每日及升级前备份，实际频率、保留期、RPO 和 RTO 由业务确认并登记。脚本失败时 EXIT trap 会尝试恢复原服务，仍需人工检查服务状态和备份完整性。

### 10.3 恢复账号数据

优先在隔离环境演练。生产恢复前明确备份版本、恢复点、备份后可能丢失的账号变更和维护窗口。以下只恢复数据；版本不兼容时按第 13 章完整回退。

~~~bash
set -euo pipefail

case "$RESTORE_DIR" in
  /var/backups/video-remix-auth/*) ;;
  *) echo '备份目录超出约定范围'; exit 1 ;;
esac

(cd "$RESTORE_DIR" && sha256sum -c database.sha256)

systemctl stop video-remix-auth
mv /var/lib/video-remix-auth \
  "/var/lib/video-remix-auth-before-restore-$RECOVERY_STAMP"
~~~

恢复后验证 HTTPS、管理员和成员登录、用户数量、角色和状态，以及一次新增和删除临时账号；再次重启核对持久化，旧令牌应失效。失败时保留恢复前目录和现场，不清空数据库重建 admin。异机灾备还须恢复相同运行时、程序依赖、密码文件和服务配置；原主机隔离后再切换 DNS，避免两个实例写同一目录。

### 10.4 客户端备份和管理员密码恢复

客户端完全退出后，备份应用设备目录、设置页业务存储目录及独立素材目录。数据可能分散在多处，不能只备份默认 AppData 或服务器。加密文件不保证新设备或新系统用户下可解密，恢复后按凭据流程重新配置密钥。

忘记管理员密码时，由其他有效管理员在“账号管理”重置。交付时建议建立备用企业管理员。全部管理员不可用时，当前没有内置命令行恢复工具，应联系维护方按受控流程处理并先备份。不得删除数据库或宣称修改初始密码文件就能恢复密码。

### 11.2 故障演练方法

A16、A17 在验收环境临时阻断客户端到入口的连接再恢复，不通过停止生产服务模拟普通网络中断，否则服务重启也使会话丢失，无法验证有效会话恢复。A15 单独在维护窗口重启服务。

停用、密码重置和删除各检查两个同时在线会话。固定 12 小时到期使用持续验收窗口验证，当前没有缩短会话 TTL 的环境变量。限流只在批准环境测试，记录代理状态码与服务错误码的区别。

## 12 常见故障定位

| 现象 | 优先检查 | 处理和复验 |
| --- | --- | --- |
| 服务反复重启 | 日志 Node路径 密码文件 数据权限 | 修正后复验health和登录 |
| 本机成功 外部失败 | DNS 安全组 证书 Nginx | 校验配置再检查外部HTTPS |
| HTTPS 502 | 后端active 回环3080 代理 | 恢复后端并验证登录 |
| 客户端鉴权配置无效 | URL是否HTTPS根地址 配置是否打包 | 正确设置变量重新打包 |
| 要求初始化本机管理员 | 是否误发普通或旧包 | 使用dist:win重建并验收 |
| 401或AUTH_REQUIRED | 密码 会话到期 服务重启 状态 | 核对后重新登录 |
| 403或FORBIDDEN | 当前账号角色 | 使用授权管理员 |
| 429或RATE_LIMITED | 代理限流 共享出口 后端计数 | 等待或评估配额 不连续重试 |
| AUTH_UNAVAILABLE | 设备网络 TLS 代理 后端 | 网络恢复重试 重启则重新登录 |
| SERVICE_UPDATE_REQUIRED | 服务是否支持users/delete | 升级对应服务版本 |
| 改密码文件没有生效 | 是否已有账号库 | 在账号管理重置 |
| 登录成功但生成失败 | 本机接口 Key额度 供应商网络 | 从设备测试业务接口 |
| 重启后账号消失 | 数据目录是否变化 文件权限 | 恢复正确目录 不初始化空库 |
| 配置无法解密 | 系统用户或设备安全存储变化 | 重新配置并保存密钥 |
| 换账号仍见同机资料 | 设备共享资料设计 | 使用设备或OS用户隔离 |

排障收集版本、时间、错误码、脱敏日志和步骤。修复后重跑受影响链路，不以服务 active 代替业务复验。

## 13 升级和回滚

### 13.1 升级准备

1. 在验收环境完成新版本类型检查、测试和两端构建，核对接口和数据库兼容性，登记服务端与客户端版本。
2. 按第 10.2 节备份并记录摘要、恢复责任人；变更期间冻结账号管理操作。
3. 将新包校验后解压到全新候选目录，安装相同方式的 Linux 生产依赖，不覆盖叠加旧目录。
4. 运行时、服务单元、代理和证书只按实际需要变更；数据目录保持指向现有数据库，不以空目录升级。

### 13.2 替换程序

以下 root Bash 示例保留旧程序和账号数据，候选目录使用唯一时间戳。

~~~bash

read -r -p '输入已校验的新服务端zip绝对路径: ' UPGRADE_ZIP

test ! -e "$PREVIOUS_APP"

cd "$CANDIDATE"
test -f dist-server/server/main.js
PATH=/opt/node-remix/bin:/usr/bin:/bin /opt/node-remix/bin/npm ci \
  --omit=dev --omit=optional --ignore-scripts --no-audit --no-fund
/opt/node-remix/bin/node -e \
  "require('sql.js')().then(() => console.log('sql.js ready')).catch(() => process.exit(1))"
chown -R root:root "$CANDIDATE"

  --retry-delay 1 --max-time 5 http://127.0.0.1:3080/health
~~~

切换后验证外部 HTTPS、两种角色登录、用户数量和状态、权限与会话撤销，确认没有再次出现 auth.admin-initialized。服务重启会撤销所有会话，通知员工重新登录；验收通过才结束维护窗口。

### 13.3 失败回滚

启动失败、账号数据不符、权限异常或关键业务阻断时回滚。输入记录的旧程序路径，保留失败版本。

~~~bash
set -euo pipefail
read -r -p '输入旧程序目录 /opt/video-remix-auth-prev-时间戳: ' PREVIOUS_APP
PREVIOUS_APP=$(realpath -e "$PREVIOUS_APP")
case "$PREVIOUS_APP" in
  /opt/video-remix-auth-prev-*) ;;
  *) echo '旧目录不符合约定'; exit 1 ;;
esac
test -f "$PREVIOUS_APP/dist-server/server/main.js"
FAILED_APP="/opt/video-remix-auth-failed-$(date -u +%Y%m%dT%H%M%SZ)"
test ! -e "$FAILED_APP"
systemctl stop video-remix-auth
mv /opt/video-remix-auth "$FAILED_APP"
mv "$PREVIOUS_APP" /opt/video-remix-auth
systemctl start video-remix-auth
systemctl is-active video-remix-auth
curl --fail --silent --show-error --retry 10 --retry-connrefused \
  --retry-delay 1 --max-time 5 http://127.0.0.1:3080/health
~~~

代码回滚适用于数据库兼容情况。不兼容变更需在停服状态按批准方案恢复升级前数据库及对应服务和代理配置，再 daemon-reload、nginx -t 并启动。恢复旧数据会丢失备份后的账号变更，须明确恢复点。当前没有通用数据库自动降级工具。

客户端回滚使用保留且已校验的上一版安装包，完全退出后按企业软件流程处理；先备份业务资料并核对本地数据库兼容性。回退后验证鉴权地址、权限与持久化。
